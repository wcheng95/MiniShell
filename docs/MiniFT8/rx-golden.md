# MiniFT8-V3 RX-1A Golden Boundaries

## 1. Purpose

RX-1A freezes behavioral evidence from MiniFT8-V2 **before** V3 decoder source is migrated or structurally cleaned.

RX-1A is not an architecture-design step and does not change decoder mathematics. Its job is to make later structural refactoring measurable:

```text
same reference input
    -> same monitor/waterfall behavior
    -> same valid protocol payload
    -> same supported protocol type/semantics
```

The pinned MiniFT8-V2 algorithm baseline is:

```text
5bd3ef98f72388a850bebad04bd7300b90edb63c
```

Later commits in the V2 repository add RX-1A host tests/workflow around that baseline. One separate post-baseline V2 safety fix increases the telemetry decode buffer from 16 to 19 bytes; it does not change decoder mathematics or supported message types.

## 2. What is hard-golden versus diagnostic

RX-1A hard invariants are:

```text
known PCM -> exact active waterfall bytes on the Linux reference host
waterfall -> exact unique 10-byte protocol payload
fixed payload -> protocol type + canonical decoded text
```

The following are recorded as useful V2 diagnostics/baselines but are **not** frozen as permanent V3 structural contracts:

```text
candidate score
candidate ordering
candidate index
V2 SNR value
CRC-derived quick hash
V2 generic field-offset representation
```

Exact payload comparison is the canonical protocol-message identity. A CRC/hash may be used as a quick prefilter, but it is not collision-free identity.

## 3. Reference environment and CI

The RX-1A reference harness lives in the MiniFT8-V2 repository:

```text
tests/tx_e2e/rx1a_reference_dump.cpp
tests/tx_e2e/test_rx1a_boundaries.cpp
.github/workflows/rx1a-reference.yml
```

The reference workflow builds the existing V2 host decoder, runs the existing `golden_rx` test, runs the new `rx1a_boundaries` regression, and emits a diagnostic reference dump.

The completed reference run used:

```text
Ubuntu 24.04 x86-64
GCC/G++ 13.3.0
```

Workflow run #4 passed all RX-1A steps.

Exact waterfall byte fingerprints are therefore a **Linux reference-host structural golden**. Other targets such as ESP32/Cardputer may legitimately differ at the byte level because of floating-point/FFT implementation details; they must still preserve valid payload/type semantics unless an algorithm change is explicitly intended and measured.

## 6. Decoder golden

The production V2 decode profile used for the reference is:

```text
candidate capacity      50
minimum sync score       5
max LDPC iterations     25
```

Both FT8 and FT4 fixtures produce exactly one unique protocol payload:

```text
000000206016500A1988
```

and decode as:

```text
protocol type : STANDARD
canonical text: CQ W1XYZ FN42
```

Candidate score/order/location and CRC-derived quick hashes are diagnostic only. They are useful when investigating a regression but are not the architectural contract.

## 7. Fixed message-codec vectors

The codec regression uses fixed payload bytes rather than generating payloads at test time. This prevents an encoder and decoder changing together from hiding a regression.

### Standard CQ

```text
payload: 000000206016500A1988
i3=1 n3=6
type: STANDARD
text: CQ W1XYZ FN42
```

V3 structured semantics should expose CQ/token, callsign `W1XYZ`, and grid `FN42` directly.

### ARRL Field Day

```text
payload: 0C1690C536B4268176C0
i3=0 n3=3
type: ARRL_FD
text: W6ABC AG6AQ R 1B SCV
```

V3 structured semantics should preserve at least:

```text
call_to = W6ABC
call_de = AG6AQ
has_r   = true
tx_num  = 1
class   = B
section = SCV
```

The V2 generic three-field/offset representation is not the V3 target API.

### DXpedition

```text
payload: 326C137BC6A185277040
i3=0 n3=1
type: DXPEDITION
text: K1ABC RR73; W9XYZ <KH1/KH7Z> -08
```

V3 structured semantics should preserve the RR73 station, report-target station, fox callsign, and report independently. Exact final field names are decided during RX-1B.

### Non-standard-call CQ

```text
payload: 00003E4A34A86EEB8460
i3=4 n3=1
type: NONSTD_CALL
text: CQ PJ4/KA1ABC
```

V3 structured semantics preserve CQ + non-standard callsign without requiring rendered-text reparsing.

### Free-text CQ-shape exception

```text
payload: 2C91495D9F3A73119400
i3=0 n3=0
type: FREE_TEXT
text: CQ POTA W1XYZ
```

The protocol codec must continue to report `FREE_TEXT`.

Later `rx_result_builder` applies the agreed narrow application classifier:

```text
CQ <nnn|AAAA> <valid-callsign> [valid-grid]
```

so this may become logical `is_cq=true` without changing its protocol type.

## 8. V2 scope and safety notes

These points describe the V2 reference accurately; they are not reasons to broaden RX-1 structural work.

### Type 0.6 and other unsupported message types

MiniFT8-V2 does not support every FT8 message type. `FTX_MESSAGE_TYPE_CONTESTING` appears in the enum, while an `i3=0, n3=6` payload is returned as `UNKNOWN` by the current classifier.

That is acceptable V2 scope. RX-1 does **not** add type 0.6 support merely because the enum names it. Future support, if desired, is a separate protocol feature with its own vectors and tests.

The same principle applies to other recognized-but-not-fully-decoded message families: structural cleanup preserves the supported V2 behavior first.

### Telemetry output-buffer safety — fixed in V2

RX-1A found that the generic V2 message-decode path provided a 16-byte `field1_buf`, while telemetry hex decode writes 18 hex characters plus a terminating NUL.

This safety issue was fixed separately in MiniFT8-V2 PR #44 by increasing that temporary buffer to 19 bytes and adding `test_telemetry_decode.cpp`. The telemetry regression and the existing RX-1A boundary regression both pass. The fix changes no DSP mathematics and adds no new message-type support.

V3 message-codec design should still make output capacities explicit rather than depending on implicit caller buffer sizes.

### Production V2 callsign hashtable is correct

The production V2 hashtable supports 22-, 12-, and 10-bit callsign-hash lookup. It derives the appropriate shift and starting bucket for each hash width, scans the complete probe table so deletions do not break lookup chains, and refreshes age on a successful hit.

The original `tests/tx_e2e/decode_helper.cpp` used a much simpler host-only map keyed by the full 22-bit hash. That simplified **test stub** should not be confused with the production V2 hashtable.

RX-1A uses a richer host-only stub where a test needs 10/12-bit resolution. V3 still replaces process-global test patterns with an explicit context-aware `Ft8HashStore`, but that is an ownership/interface cleanup—not a correction of the V2 production hash algorithm.

## 9. Golden-update rule

Do not automatically regenerate or update RX-1A expected values merely because a refactor causes a test failure.

For structural cleanup:

```text
unexpected golden difference
    -> stop
    -> identify cause
    -> prove whether behavior changed
```

A deliberate algorithm or protocol correction may update a golden only when:

1. the change is isolated from structural cleanup;
2. the reason and expected behavioral effect are documented;
3. a dedicated comparison/test demonstrates the intended improvement or fix.

This rule keeps the V2 reference useful while still allowing MiniFT8-V3 to improve intentionally later.

## 10. RX-1A gate

RX-1A is complete.

We now have stable evidence at the three important cleanup boundaries:

```text
PCM -> waterfall
waterfall -> valid payload
payload -> protocol type/semantics
```

The next step is **RX-1B: top-down RX module and interface design**.

No V2 decoder source should be migrated into V3 until RX-1B defines ownership, data contracts, lifecycle, memory ownership, dependency direction, and unit-test boundaries.
